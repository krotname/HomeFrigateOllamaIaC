# Кот и знакомые машины: отдельный обработчик на GPU

Обработчик добавляет подписи к событиям Frigate по подтверждённой локальной
галерее котов и машин. До проверки образцов он работает в состоянии
`waiting_for_references` и не занимает видеопамять. Названия моделей и цвет
задаёт человек при разметке образцов: это сопоставление знакомых объектов,
а не универсальный определитель марки по одному снимку.

Признаки извлекает MobileNetV2 FP32 через CUDA. Его классификатор ImageNet
удалён; используется вектор после GlobalAveragePool. Исходный ONNX закреплён
на commit в `prepare-object-model.py`. Скрипт подготовки запускается на сервере
в существующем образе Frigate, без установки библиотек и выполнения кода модели.
Исходная модель и её лицензия: [ONNX Model Zoo](https://github.com/onnx/models/tree/c5cae0f1942c8d7727372c7b1f6b485aa39e4421/validated/vision/classification/mobilenet).

## Развёртывание

1. Разместить `ocr/frigate_object_worker.py` и `ocr/frigate_caption_worker.py`
   в `/opt/frigate-objects/ocr/`, доступных только для чтения.
2. Скачать FP32-модель по `MODEL_URL` из `prepare-object-model.py`.
3. В изолированном контейнере без сети запустить
   `python3 prepare-object-model.py mobilenetv2-12.onnx mobilenetv2-gap.onnx`.
   Итог поместить в `/opt/frigate-objects/models/`.
4. Создать `/var/lib/frigate-objects` с владельцем `65534:65534`, режимом `0700`.
5. Вне Git сохранить `FRIGATE_OBJECT_GPU=GPU-...` в `.env` рядом с
   `objects-compose.yml`; использовать точный UUID выбранной P40.
6. Проверить `docker compose -f objects-compose.yml config --quiet`, затем
   `docker compose -f objects-compose.yml up -d`.

Контейнер использует готовый CUDA-runtime Frigate, отдельный от основного
процесса. Файловая система только для чтения; нет доступа к архиву, конфигурации
камер, Docker socket или ключам других сервисов. API Frigate используется на
loopback `127.0.0.1:15000`. Новых слушающих портов нет. Перезапуск основного
Frigate, смена детектора и второй процесс записи не требуются.

## Образцы и проверка

Команды ниже запускаются через
`docker exec frigate-objects python3 -m ocr.frigate_object_worker ...`.
Персональные имена, данные галереи и фотографии не помещаются в Git.

1. Создать профиль: `profile --id cat-a --kind cat --label 'Кот А'`.
2. Добавить три разных подтверждённых события:
   `enroll --event EVENT_ID --profile cat-a --role train`.
3. Добавить два других события этого кота с `--role validation`.
4. Добавить минимум три события с другими котами:
   `enroll --event EVENT_ID --role validation` без `--profile`.
5. Выполнить `calibrate --profile cat-a` и проверить `enabled` и причину.
6. Проверить `status`; для одиночного GPU-прогона использовать
   `probe --event EVENT_ID`.

Аналогично создаются профили `--kind car` с подписью «марка, модель · цвет».
Повторное использование одного event ID в обучении и проверке запрещено.
Для событий одной поездки на разных камерах задавать одинаковый `--group VISIT_ID`:
они не могут попасть в разные роли или считаться независимыми встречами.
Без явно проверенной группы образец остаётся неразобранным и блокирует включение
автоматических меток этого вида объектов. ID события сам по себе группой не считается.
Для существующих и перенесённых образцов `status --references` показывает источники
и метаданные без векторов. `curate --source SOURCE --group VISIT_ID` назначает группу
сохранённому образцу, не загружая его повторно; `--role train|validation` меняет роль
с проверкой разделения встреч. После разбора снова выполнить `calibrate`.
Для включения нужны минимум три обучающие, две положительные проверочные и три
отрицательные проверочные встречи. Миграция старой галереи сохраняет векторы и
снимает прежнюю калибровку; разные ракурсы одного заезда порог не обходят.
Любой новый образец снимает старую калибровку соответствующего вида объектов:
после пополнения нужно снова выполнить `calibrate`. Если положительные и
отрицательные примеры похожи, профиль остаётся выключенным. Проверочные
положительные примеры также должны проходить рабочий отрыв от конкурентов.
При изменении галереи другой командой текущая обработка прекращается до
загрузки актуальных образцов и калибровок, накопленные голоса незавершённых
событий сбрасываются. Изменение профилей, добавление образцов и калибровка
выполняются в последовательных SQLite-транзакциях.

Для проверки нужны разные дни, ракурсы и освещение, включая похожие чужие
машины/котов. Два соседних события одной поездки дают слабое подтверждение
качества на будущих поездках. Небольшая проверочная выборка не доказывает
общую точность. Ночью, при закрытом кузове, низком разрешении и отличающихся
ракурсах ожидаются пропуски. Метрика similarity не является вероятностью.

## Нагрузка и правила записи

- Не более двух новых вырезок в секунду, одна CUDA-сессия, без пакетной обработки
  видеопотоков. API опрашивается раз в 15 секунд, рассматриваются только события
  котов и машин за последние пять минут и продолжающиеся события независимо
  от их возраста на камерах участка; уличная 04 исключена. Каждый запрос
  ограничен 100 событиями, результаты объединяются без дублей.
- Перед загрузкой требуется минимум 3,5 ГиБ свободной VRAM, после загрузки —
  2 ГиБ. Перед вычислением при загрузке GPU от 25% обработчик уступает ресурсы;
  после вычисления проверяется только память, поскольку счётчик загрузки
  включает собственные CUDA-ядра обработчика. Ограничен CUDA arena
  в 1,5 ГиБ; дополнительно проверяется изменение свободной памяти при загрузке.
  Arena не ограничивает память CUDA-драйвера и сторонних процессов.
- CPU fallback запрещён в ONNX Runtime. Если CUDA недоступна или закончилась
  память, автоматические подписи приостанавливаются. CPU обслуживает HTTP,
  декодирование JPG и сравнение векторов.
- Сессия выгружается при отсутствии работы более минуты, нехватке памяти,
  нагрузке других задач или отсутствии проверенных профилей.
- Для подписи нужны два совпадения на разных `snapshot_frame_time`, порог
  калибровки и отрыв от конкурента. Одного архивного снимка недостаточно.
  Вырезка строится по нормализованному боксу; HTTP `X-Frame-Time` должен совпасть
  со временем бокса. Сменившийся между запросами кадр пропускается. Это также
  убирает фон соседних машин из большой стандартной вырезки Frigate.
  Уже подписанные события сохраняют подпись; после одного POST выполняются
  ограниченные GET-проверки асинхронного сохранения, без повторения POST.
  API и снимки запрашиваются с `X-Cache-Bypass: 1`: встроенный nginx Frigate
  кэширует API на пять секунд даже при ответе `Cache-Control: no-store`.
- Обычные обработанные события ограничены 512 записями и тремя сутками,
  галерея — 500 образцами. До 512 маркеров сомнительных записей `pending`
  хранятся отдельно от этого лимита без удаления по возрасту. При заполнении
  лимита новые записи блокируются до разбора прежних. Недоступный или
  повреждённый снимок пропускается без остановки обработки других событий.
  Исходные JPG не сохраняются обработчиком.

Названия людей можно добавить только командой `manual-label --event EVENT_ID
--label 'Подпись владельца'` к конкретному подтверждённому человеком кадру.
Автоматический обработчик не принимает людей в галерею и не создаёт их
эмбеддинги. Номерные знаки не читаются. Уведомления не отправляются.

API Frigate не предоставляет атомарный compare-and-set для sub-label: перед
записью проверяется текущая подпись, но остаётся короткое окно конкурентной
правки. После сомнительного ответа API сначала проверяется событие, повторный
POST вслепую не выполняется. Перед автоматическим POST сохраняется `pending`:
если процесс оборвался или ответ не подтвердился, последующие опросы только
наблюдают подпись. Неразрешённые `pending` видны в `status` и требуют разбора
конкретного события; автоматическая повторная отправка не выполняется.
Метка `pending` создаётся после успешного контрольного GET непосредственно
перед POST; сбой чтения до начала записи позволяет повторить обработку события.

Остановка: `docker compose -f objects-compose.yml down` останавливает только
этот обработчик. Галерея остаётся в `/var/lib/frigate-objects`; основной Frigate
и его записи продолжают работать.

## Выборочная проверка архива

`python3 -m ocr.frigate_object_archive --output /data --after UNIX_START
--before UNIX_END --event-after UNIX_EVENT_START` запускается на сервере в том же
непривилегированном CUDA-runtime с точным UUID, сетью host, корнем только для чтения,
`--cap-drop ALL`, `no-new-privileges`, лимитами CPU/RAM/PID и `--no-healthcheck`.
Последний параметр отключает унаследованную HTTP-проверку основного Frigate:
пакетная задача не запускает веб-сервер. `/work` с исходниками и `/models` монтируются
только для чтения, приватный каталог результата — как `/data` с владельцем 65534
и режимом 0700. Архив и конфигурация камер в контейнер не монтируются.

Нужны действующая `/models/yolov9-t-320.onnx` из этого Frigate и модель признаков.
Две CUDA-сессии используют те же проверки свободной памяти и приоритета других
задач. Детектор повторно ищет только котов и машины в кадрах через loopback API;
каждая сессия ограничена двумя вычислениями в секунду, CPU fallback запрещён.
Фактические провайдеры ядер сохраняются в `execution.json`. Учёт памяти каждой
сессии складывает изменения при её загрузке и собственных вызовах, исключая
выделение памяти второй сессией между ними. Это оценка по свободной памяти GPU;
независимая проверка общего свободного запаса остаётся обязательной.

По умолчанию выбираются три кадра каждого события участка и один кадр каждые
пять минут на каждой камере. Пропуски записей учитываются отдельно, перекрытия
сегментов не увеличивают длительность. Это выборка: короткое появление кота между
кадрами может быть пропущено. Полная неделя возможна только при наличии записей.

Лимиты запуска: 2400 кадров, 40 минут, по 600 вырезок каждого вида. После исчерпания
лимита вырезок детекция остальных кадров продолжается; лимит машин не мешает
сохранять котов. Повторный запуск с теми же границами продолжает `plan.json` и
`results.jsonl`; смена интервала, диапазона или содержимого моделей запрещена.
Один каталог обслуживается одним Linux-процессом: неблокирующая блокировка
`.scan.lock` отклоняет второй запуск до чтения плана и результатов. После выхода
или аварии процесса блокировку снимает ядро; сам пустой файл удалять не нужно.
План закрепляет ревизию признаков и дайджесты обеих моделей, чтобы при возобновлении
не смешивались несовместимые векторы. Старый план без этих полей не возобновляется.
Новый лимит вырезок не может быть меньше уже сохранённого количества каждого вида.
При обрыве записи отбрасывается только незавершённая последняя строка JSONL;
законченные строки сохраняются, повреждение внутри файла останавливает продолжение.
Ограничение времени и
приоритет GPU дают сохранённый отчёт с причиной паузы. Число обработанных кадров,
ошибки получения и пропуски по бюджету нужно читать из `report.json`.

Результат содержит приватные вырезки, векторы и предложения для разметки, без
записи меток в Frigate и без самостоятельного обучения на собственных догадках.
Фоновые повторы отсеиваются по сходству изображения. В галерею можно переносить
только подтверждённый объект, проверив его бокс в исходном кадре; у соседней
припаркованной машины нет подтверждения только потому, что она попала в тот же
кадр. Предложения имеют `group_id: null`, пока встречу не разберёт человек.
Все варианты одной встречи, включая разные камеры, получают один `group_id`.
Пробелы по краям ID убираются до проверки независимости; пустой ID не подтверждает
встречу. Старые образцы с такими пробелами сохраняют вектор, но требуют повторной
разметки через `curate`, а их калибровка сбрасывается.

После проверки конкретной вырезки и исходного кадра её можно импортировать:

```sh
python3 -m ocr.frigate_object_worker import-archive \
  --archive /state/archive-RUN --image frame-00001-0-car.jpg \
  --profile CONFIRMED_PROFILE --role train --group CONFIRMED_VISIT
```

Для отложенной проверки используйте `--role validation` и отдельные встречи.
Без `--profile` разрешена только роль `validation`: образец становится подтверждённым
отрицательным примером. Неизвестную
машину без такой проверки не импортируйте. Команда переносит готовый вектор без
загрузки GPU, проверяет совпадение модели с планом и запрещает повторный импорт
того же объекта из того же кадра даже после переименования каталога или файла.
Старые результаты без идентичности модели для этой команды нужно извлечь заново;
добавлять подтверждение модели задним числом по имени файла нельзя. После импорта
калибровка сбрасывается; перед включением требуется повторный `calibrate`.
`curate` также сохраняет для отрицательных примеров только роль `validation`.

При переходе между CUDA-сессиями допускается до двух секунд ожидания снижения
показателя загрузки; проверки памяти и приоритета не отключаются. Имена, изображения,
ответы владельца, векторы и отчёты остаются вне Git.
